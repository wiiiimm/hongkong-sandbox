# Smooth mobile model streaming — HKS-229

Codex root, 2 October 2026. Planning only, requested during PR #298 review.
No model streaming behaviour changes accompany this document. The separate
aircraft fix under HKS-177 reveals the detailed aircraft once after loading.

## What we know

The user reports navigation lag while enhanced buildings load on mobile. This
is a real reported symptom, but its CPU/GPU breakdown has not been measured on
a physical phone. An asynchronous network request does not make decoding,
fallback reconstruction or GPU upload free.

At the planning baseline, `city/official-models.js` runs its planner at most
once per 180 ms. It scans the catalogue and constructs bounds for each entry.
Mobile limits already include one concurrent load, 24 resident models, 450,000
triangles, 48 MiB geometry and 128 MiB estimated resident cost (160 MiB for
selection). These are application estimates, not a measurement of device VRAM.

The planner retains visible resident detail even beyond its normal loading
distance. This honours the earlier request to stop visibly disappearing models,
but couples current visibility and residency. `load()` waits for retiring
fallback work; `release()` restores fallback geometry before disposing detail,
and restores dependents before their source support. Rapid eviction can therefore
cause extra work even when downloads are cached.

## Proposed policy

| What the viewer needs | What to draw | What to retain or request |
| --- | --- | --- |
| Nearby building large enough on screen | Enhanced model when ready | Pin required supports; show existing basic form until a complete replacement is ready |
| Distant building still in view | Basic form, or a measured offline LOD later | Request detail only if it would add enough visible information |
| Just outside the view | Nothing from its enhanced group | Keep a bounded warm resident entry briefly |
| Outside the warm-cache budget | Basic form when visible again | Dispose safely; reuse cached source bytes on return |
| Selected building or required walking/flight collision region | Appropriate detail and collision data | Pin its dependency closure regardless of ordinary visual ranking |
| Demo preload | Same visual policy | Download nearby-first and outward, without decoding all assets into memory |

Distance alone is insufficient: a distant tower filling the screen can deserve
detail; a nearby tiny shed may not. Use camera field of view, actual viewport
dimensions and projected bounding size. Track both horizontal and vertical
extent so portrait and landscape views behave consistently. Large silhouettes
and selected landmarks can receive priority within measured budgets.

Separate three decisions: visibility for drawing, decoded residency for reuse,
and compressed-byte prefetch. Browser HTTP caching is useful for the last one;
it does not remove decode, scene attachment or GPU upload costs.

## Keep the checks cheap

1. Precompute bounds and a spatial tile/index structure when catalogues load.
   Query potentially visible tiles, then their model bounds. Do not iterate the
   entire Hong Kong catalogue every animation frame.
2. Schedule checks on meaningful camera/viewport changes, initially around
   4–6 times per second while moving. Measure this rate rather than assuming it
   is optimal; do no repeated planning while the camera is still.
3. Reuse scratch vectors/frustum objects. Start with conservative bounding-box
   tests, without per-building occlusion raycasts or GPU readback.
4. Use an expanded view margin and different promotion/demotion screen-size
   thresholds. Delay demotion and eviction long enough to absorb small camera
   changes; evict sooner only under memory pressure.
5. Prioritise motion-responsive rendering. Queue decode/attachment/fallback
   work separately and cap work per frame. Move suitable decode/bake work to
   workers, respecting current transfer, cancellation and source-transform rules.

These checks have a cost. The hypothesis is that a bounded set of simple tests
will cost much less than unnecessarily drawing detail and repeatedly rebuilding
it. Prove that hypothesis on a lower-power device before setting defaults.

## Preserve correctness and appearance

Demoting an in-view building requires its basic replacement to be ready first.
No abrupt disappearance, duplicates or holes. Use a short bounded transition
only where measured performance permits; blur and dual-render fades may increase
mobile GPU cost. Respect reduced motion. Do not animate a whole-city blur.

Support models and dependent towers change as a coherent group. Never release
a podium beneath an enhanced tower; account for the whole group in memory and
draw budgets. Preserve picking, native 1× HKPD placement, walking/flight
collision and retry/failure behaviour independently of visual detail selection.

Evaluate terrain/base building chunks, shadows, labels and other scene layers
alongside government detail: reducing enhanced models alone may not solve lag.
Ensure basic visible coverage can reach the far view without requiring every
near-detail chunk. Keep nearby collision coverage separate from distant visuals.

Retain original government assets. If profiling shows a need for intermediate
LODs, produce them offline with compute, retaining provenance and dimensions.
No AI remodelling is proposed. Quality/detail and preload controls should let
the user choose Auto or a fixed budget, with progress explaining background
downloads versus ready detail. A demo button must not remove mobile safeguards.

## Delivery order and validation

First add measurements for planning, decode, attach, fallback rebuild and long
tasks. Then implement spatial queries and independent bounded residency. Add
screen-space promotion/demotion with hysteresis, followed by scheduling changes
and adaptive draw/pixel budgets only where measurements justify them.

Capture cold and warm runs of identical pan/zoom/fly routes on a named physical
low-power phone and desktop. Record median/p95 frame time, long-task duration,
planner time/candidate count, decode/install/retire time, asset requests, draw
calls, triangles and estimated resident cost. Include fast turns, repeated
boundary crossings, narrow portrait views, large distant landmarks, selected
towers/supports, memory pressure and failed asset Retry.

Before implementation, define a baseline-relative improvement target and a
device-specific frame budget from those measurements. No FPS improvement is
claimed by this plan or by headless desktop browser tests.

Acceptance: bounded checks; no repeated download/decode churn on camera reversal;
no visible holes or abrupt landmark removal; support, picking and collision
checks pass; memory/draw budgets hold; physical-device navigation improves.
